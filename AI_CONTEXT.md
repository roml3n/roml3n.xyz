# PhotoGlobe Component — Project Brief

**Project:** roml3n.xyz portfolio site (Next.js)
**Component location:** `app/components/PhotoGlobe/`
**Files involved:** `PhotoGlobe.tsx`, `sphereLayout.ts`, `PhotoGlobeOverlay.tsx`, `GlobeCard.tsx`, `useGlobeRotation.ts`, `DECISIONS.md`, and the page that renders it (`app/photos/page.tsx` or similar).

---

## 1. What this is

A photo gallery on the /photos page rendered as an interactive rotating 3D sphere made of Polaroid-style photo cards, using pure CSS 3D transforms (no Three.js — this was a deliberate decision, see `DECISIONS.md`). Cards sit on the sphere's surface arranged along latitude/longitude lines like a globe. Clicking a card opens it full-size via a FLIP-style animated overlay (`PhotoGlobeOverlay.tsx`).

**Reference for the target interaction/look:** https://vast-author-374088.framer.app/link — this was used to confirm the overall shape/behavior goal is correct. As of the last check-in, the built component already matches this reference structurally (sphere shape, card layout, rotation). The open work now is refining feel/interaction, not re-architecting the shape.

---

## 2. Architecture

- **`sphereLayout.ts`** — pure math module. Generates the set of points (`SpherePoint[]`) where cards sit on the sphere: x/y/z coordinates plus a `roll` value. This is the file that defines *how cards are distributed* on the sphere (latitude rings, longitude columns per ring, roll).
- **`PhotoGlobe.tsx`** — main component. Takes `photos` prop, calls `createSphereLayout()`, applies the current rotation (from `useGlobeRotation`) to every point each frame, computes each card's rotated x/y/z, depth-sort order, and per-card tilt (pitch/yaw) so cards face outward correctly. Renders `GlobeCard` for each photo and manages the selected/open photo state that triggers `PhotoGlobeOverlay`.
- **`GlobeCard.tsx`** — a single card. Handles the Polaroid-style white border, per-card scale (combining camera-depth scale + pole-distance scale), hover/tap micro-interactions (via Framer Motion), and click-ability based on depth (back-facing cards are inert/non-interactive).
- **`useGlobeRotation.ts`** — owns the rotation state `{x, y}` that drives the whole globe's orientation each frame. Currently: constant idle auto-rotation on Y + a pointer-position-based tilt (parallax-style, not drag). **This is the file currently being upgraded** (see Section 5, "Next Task").
- **`PhotoGlobeOverlay.tsx`** — full-screen photo viewer. Uses manual `getBoundingClientRect()` snapshots (not Framer Motion's `layoutId`, which didn't behave reliably with nested 3D transforms) to FLIP-animate a clicked card into a centered, larger view, and reverse the animation on close.
- **`DECISIONS.md`** — running log of technical decisions and their reasoning. Keep this updated as things change; it's the source of truth for *why* something is built a certain way, so don't silently contradict it — update it when a decision changes.

## 3. Chronological history / how we got here

This matters mostly so whoever picks this up doesn't "fix" something that was already deliberately tuned, or re-break something that was already fixed.

1. **V1 — Fibonacci sphere, random per-card roll.** Cards distributed via golden-angle Fibonacci sphere sampling (good for even coverage), each card's `roll` (rotateZ) generated by hashing its photo ID (`seededRoll`). Structure was sphere-shaped but looked sparse/flat compared to target — root cause was partly a data issue (photos array needed to repeat 4x → 68 total points for a dense-looking globe) and partly under-tuned depth scaling / camera distance.
2. **Density + depth pass.** Verified/fixed the 68-point dense photo set, increased the depth-based scale range so front cards read clearly bigger than back cards, checked for container/overflow clipping, tuned `CAMERA_DISTANCE` vs `RADIUS` ratio for better perspective.
3. **Lat/long grid alignment ask.** The random per-ID `roll` was identified as the reason cards looked chaotically scattered instead of aligned like a globe's surface (latitude/longitude grid). Fix direction: remove random roll, derive each card's pitch/yaw from its true spherical position instead of damped approximations.
4. **Overcorrection #1 — rigid rectangular grid.** First fix replaced the Fibonacci scatter with a strict `4 rows × 17 columns` grid. This broke badly — only 4 latitude rings meant the globe rendered as ~4 separate flat rings/bracelets stacked with visible gaps, not a filled sphere (classic "too few latitude bands" UV-sphere mistake).
5. **Overcorrection #2 — circumference-weighted rings.** Fixed the ring count (many more latitude bands) and varied the number of longitude columns per ring based on that ring's circumference (fewer cards near poles, more at equator, `sin(latitude)`-weighted). This restored the sphere shape but broke the clean lat/long *snap* — because column counts differ per ring, the longitude angles no longer line up vertically between rings.
6. **Correct fix.** Reverted to a **shared, fixed set of longitude angles across every ring** (this is what restores the "columns align into meridian lines" look), and instead of a full recompute per ring, only **dropped 2–3 specific cards** from the pole-most ring(s) to relieve crowding — keeping the remaining cards on the same shared angles as every other ring.
7. **Sizing/framing passes.** Max local scale cap reduced (progressively tuned, last known value `0.94` from Codex, but user has since hand-adjusted sizing further — **treat current numeric values as unverified, re-read from source**). Border thickness iterated 4px → 6px → 8px for a stronger Polaroid mat look; a card size of `80px` photo surface with `8px` white exterior border was implemented at one point. A `black/10`-opacity outline was added just outside the white border so cards stay visible against a white page background.
8. **Pole crowding fix.** Cards near the poles were visually overlapping/bumping due to tight spacing at small ring circumference. Added a `poleScale` factor (0–1) per point based on ring distance from the equator: equator + ~2 nearest rings = full size (`poleScale = 1`), tapering down (linear/eased) to roughly `0.5–0.6` at the pole-most rings. This is multiplied into `GlobeCard`'s existing depth-based `finalScale`.
9. **Reference comparison.** Confirmed via the Framer reference link that the current structural shape/interaction already matches the target — no further shape changes needed. Styling questions (border style, background, label overlays) were explicitly punted: **user wants to keep the current white Polaroid frame, keep the plain white background, and skip any name/label overlay for now.** So no visual styling changes are currently requested — don't add these unless asked again.
10. **Current open task — drag-to-spin with momentum.** See Section 5.

- Cards use a Polaroid-style white border (thickness iterated multiple times — last known ~6–8px, confirm in `GlobeCard.tsx`).
- A subtle `black/10` outline sits just outside the white border for contrast on white backgrounds.
- Background is plain white — **keep as is**, no change requested.
- `roll` is fixed at `0` for all points — do not reintroduce random/hash-based roll.

- Pole-most ring(s) have 2–3 fewer cards than the standard column count, to relieve crowding, while remaining cards still sit on the shared longitude angles.
- Card final scale = camera-depth-based scale × `poleScale` (equator = full size, tapering toward poles).
- Rotation currently = constant idle Y auto-rotation + pointer-position-based parallax tilt (no real drag, no momentum). **This is what's being replaced next.**

## 5. Next task (in progress / not yet confirmed implemented)

**Goal:** Add real drag-to-spin with momentum/inertia to `useGlobeRotation.ts`, replacing the current pointer-position-tilt-only behavior.

**Spec:**

1. **Drag to spin** — on `pointerdown` on the globe, start tracking drag delta. While dragging (`pointermove`), convert horizontal drag delta into Y-axis rotation and vertical drag delta into X-axis rotation/tilt (1:1 or with a sensitivity multiplier), replacing the pointer-position parallax while actively dragging.
2. **Momentum on release** — track drag velocity (delta per frame) over the last few frames before `pointerup`/`pointercancel`. On release, keep applying that velocity to rotation, decaying it each frame via a friction factor (e.g. `velocity *= 0.95`/frame) until it drops below a small threshold and stops.
3. **Resume idle rotation smoothly** — once momentum decays to ~0, blend/lerp back into the existing constant idle Y auto-rotation rather than snapping abruptly.
4. **Keep the existing damping "feel"** — reuse a similar approach to the current `FOLLOW = 0.06` constant where relevant, but expose drag sensitivity, momentum friction, and idle-resume blend as named constants at the top of the file (like `IDLE_SPEED` currently is) so they're easy to hand-tune afterward.
5. **Support mouse + touch** via Pointer Events (`pointerdown/move/up/cancel`) rather than separate touch handlers.
6. **Scope constraint** — this should be isolated to `useGlobeRotation.ts` internals only. The returned `{x, y}` rotation shape must stay the same so `PhotoGlobe.tsx`, `GlobeCard.tsx`, and `sphereLayout.ts` don't need any changes.

**After implementing:** the two knobs that will likely need hand-tuning by feel are (a) friction/decay rate — how long the globe keeps spinning after release, and (b) drag sensitivity — how much rotation per pixel dragged.

## 6. Things to explicitly NOT change right now

- Don't reintroduce random per-card roll.
- Don't vary longitude column angles per latitude ring (breaks the grid snap).
- Don't change border style, background color, or add label overlays — these were explicitly deferred by the user.
- Don't touch the FLIP overlay animation approach in `PhotoGlobeOverlay.tsx` (manual rect snapshots) — `layoutId` was already tried and rejected for reliability reasons with nested 3D transforms.

## 7. How to verify changes

- `npx tsc --noEmit`, `git diff --check`, `npm run build` (used consistently throughout this project so far).
- Visual check: cards on the same latitude ring should share pitch; cards on the same longitude column should share yaw; equator-ring cards should be full size, tapering smaller toward poles with no visible overlap/bumping; front cards should read clearly closer/bigger than back cards.
- For the drag/momentum task specifically: drag and release should produce a natural-feeling spin-and-decay, not an abrupt stop, and should not conflict with click-to-open behavior on cards (a drag shouldn't accidentally register as a card click).
